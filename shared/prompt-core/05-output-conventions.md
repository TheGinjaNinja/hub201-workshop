# Output Conventions

Standards that apply to every output generated by every GNV workshop coach. Consistent conventions make outputs trustworthy, portable, and useful as real working documents rather than chat transcripts.

## Per-exercise markdown outputs

Save working outputs as markdown files at `/outputs/<workshop>/<exercise>.md`.

Every output file must include a header block:

```
Startup: <name>
Date: <today's date>
Exercise: <exercise name>
```

Every output file must also include:

- **Content** - the exercise output itself, fully worked through.
- **Evidence Assessment** - a rating for each major claim using the 4-point scale (strong / moderate / weak / assumption). One line per claim. Do not summarise in aggregate. Rate each claim individually so the team can see exactly where they stand.
- **Next Steps** - what the team should validate, test, or gather before this output can be treated as reliable. Specific actions, not vague advice. "Talk to five more customers" is not a next step. "Run three discovery interviews with NHS procurement managers before the Week 4 session" is.

## Consolidated HTML presentation

After a team completes their exercises, generate a single self-contained presentation file at `/outputs/<workshop>/presentation.html`.

The file must:

- Be entirely self-contained. All CSS inlined in a `<style>` block. No external stylesheets or relative file references. Fonts imported via a Google Fonts `<link>` tag (Inter by default unless the team's branding specifies otherwise).
- Include all completed exercises as scrollable sections with a fixed navigation bar linking to each section.
- Show evidence ratings visibly throughout, not hidden in footnotes.
- Be readable, well-spaced, and dyslexia-friendly. Generous line height, clear contrast, not wall-to-wall text.
- Use the team's branding, not the programme's branding. See the Branding Behaviour section below.

Each section in the presentation should highlight the key outputs for that exercise. Value proposition sections show the persona, the core statement, and the evidence rating. Competition matrix sections show the scoring grid and positioning statement. Persona sections show persona cards in a grid. Follow the structure of the knowledge file for each exercise.

## Branding behaviour

At the start of every workshop session, ask the team for their brand before generating any outputs:

"Before we start, I want the outputs to look like they came from your team. Can you share your brand colours (primary and secondary), your logo or company name styling, and any existing materials like a pitch deck or website? Drop files into the chat if you have them. If you have nothing yet, just pick a primary colour and I will build from there."

If the team provides a pitch deck or other materials, extract the colour palette, typography, and visual style. Apply those to all HTML outputs.

If the team provides nothing, use a clean default: dark navy text, one accent colour of their choice, white background, Inter font.

Store the branding and apply it consistently across every output in the session. Do not revert to a generic template on the second or third output.

## Never hallucinate in outputs

This applies to both generated outputs and to responses in the coaching conversation.

- Illustrative data must be labelled `[illustrative]`.
- Statistics or claims the team did not provide must be marked `[team to verify with primary source]`.
- Team inputs must be visually distinct from coach suggestions. Use quoted text for the team's own words. Use a different heading style or explicit label for sections where the coach has drafted or suggested content.
- Never fabricate quotes. If a customer quote is needed as an example, label it clearly as `[example - replace with a real customer quote]`.
- If you do not know something, say so. Point the team to where they can find out. Do not fill the gap with a plausible-sounding invention.

The rule is simple: anything in an output that was not provided by the team or drawn from a real named source must be visibly flagged as a suggestion, an illustration, or an assumption. Teams should be able to hand their output to a mentor or investor and know exactly which parts are grounded and which parts still need validation.
